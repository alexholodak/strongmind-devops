# StrongMind Staff DevOps Engineer: Technical Exercise

Alex Holodak · September 2026

This repository is my response to the four-part exercise: the Identity Server migration ADR, a standardized Rails CI/CD pipeline, a production Dockerfile, and an observability plan. Everything here is written as if it will be committed to StrongMind's engineering knowledge base and used.

## Overall approach

**Change one thing at a time.** The migration ADR moves the cloud provider and nothing else. The .NET 6 upgrade, the Azure AD DS dependency, and any database engine change are each deferred to their own ADR with a named follow-up.

**Zero downtime where it is achievable** Compute cutover is genuinely zero-downtime via Route 53 weighted routing. The database step is a short, scheduled, low-traffic window where token *issuance* degrades and token *validation* does not.

**Rollback is designed before the deploy.** Every step in the ADR cutover has a rollback trigger and a procedure. The pipeline records its rollback target before it touches the service. The observability plan defines what "unhealthy" means numerically.

**One observability pipeline for both workstreams.** OpenTelemetry in the app, ADOT collector sidecar, CloudWatch and X-Ray behind it, Jira Operations routing on top. The .NET service and the Rails app instrument differently but ship to the same place with the same conventions.

## Infrastructure the pipeline depends on

The exercise asks for the workflow file, but a workflow is only half the deploy contract. These three pieces live outside the repo and are required for `rails-deploy.yml` to function. In practice they would be in Terraform alongside the ECS service.

### GitHub OIDC provider and CI roles

One-time setup in the account:

```hcl
resource "aws_iam_openid_connect_provider" "github" {
  url             = "https://token.actions.githubusercontent.com"
  client_id_list  = ["sts.amazonaws.com"]
  thumbprint_list = ["6938fd4d98bab03faadb97b34396831e3780aea1"] # AWS ignores this for GitHub since 2023 but the argument is required https://github.blog/changelog/2022-01-13-github-actions-update-on-oidc-based-deployments-to-aws/
}
```

Or from AWS CLI v2:

```bash
aws iam create-open-id-connect-provider \
  --url https://token.actions.githubusercontent.com \
  --client-id-list sts.amazonaws.com \
  --thumbprint-list 6938fd4d98bab03faadb97b34396831e3780aea1
```

Three roles. The push role is assumable from any branch and can only write to ECR. Each deploy role is assumable only through its GitHub environment and can only touch that environment's service.

| Role | Assumed by | Trusted subject | Can do |
|---|---|---|---|
| `github-actions-rails-push` | `build` | `repo:strongmind/rails-app:ref:refs/heads/*` | Push to the one ECR repository. Nothing in ECS. |
| `github-actions-rails-deploy-staging` | `deploy` (staging) | `repo:strongmind/rails-app:environment:staging` | Register task definitions and update the staging service only. |
| `github-actions-rails-deploy-production` | `deploy` (production) | `repo:strongmind/rails-app:environment:production` | Register task definitions and update the production service only. |

A role per environment rather than one deploy role with two subjects, because staging has no required reviewers. With a shared role, anyone who can dispatch a staging deploy from a branch holds a token whose permissions reach the production cluster, and the workflow file is the only thing stopping them from using it. With a role per environment, the production role is reachable only through the production environment, which the `resolve` job allows only from `main`, and which is where required reviewers would sit if a team enables them. The workflow picks the role by suffix, so adopting repos change nothing.

The push role trusts every branch on purpose. The exercise's model is that any branch push runs CI and a branch can be dispatched to staging, so the build job has to push from branches. Pushing a SHA-tagged image is inert: nothing runs it until a task definition references it, and only a deploy role can register one. The build job declares no `environment:`, so its subject is the branch ref, and the wildcard is the whole of what it can present.

The deploy job is the only one that references a GitHub environment. That matters if required reviewers are ever enabled on `production`: GitHub applies them **per job**, not per run (the docs describe each job waiting individually, and a [community thread](https://github.com/orgs/community/discussions/88692) from January 2024 reports "3-4 approvals for each workflow" with no staff answer). If `build` also referenced `production`, reviewers would be prompted twice. As written, enabling reviewers prompts once, at `deploy`, on a SHA that has already passed RSpec and Brakeman and been pushed.

The `resolve` job, not IAM, enforces that production is only ever dispatched from `main`. A pull request from a fork gets no `id-token` and cannot assume any of the roles.

Trust policy for `github-actions-rails-deploy-production`. The staging role is identical with its own subject. The push role uses `StringLike` for the branch wildcard:

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Federated": "arn:aws:iam::ACCOUNT_ID:oidc-provider/token.actions.githubusercontent.com" },
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringEquals": {
        "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
        "token.actions.githubusercontent.com:sub": "repo:strongmind/rails-app:environment:production"
      }
    }
  }]
}
```

Permissions policies, scoped to resources rather than `*`:

| Role | Action | Resource |
|---|---|---|
| push | `ecr:GetAuthorizationToken` | `*` (API does not support resource scoping) |
| push | `ecr:BatchCheckLayerAvailability`, `ecr:PutImage`, `ecr:InitiateLayerUpload`, `ecr:UploadLayerPart`, `ecr:CompleteLayerUpload`, `ecr:BatchGetImage`, `ecr:GetDownloadUrlForLayer` | the one repository ARN |
| deploy-`<env>` | `ecs:DescribeServices`, `ecs:UpdateService` | that environment's service ARN only |
| deploy-`<env>` | `ecs:DescribeTaskDefinition`, `ecs:RegisterTaskDefinition`, `ecs:DeregisterTaskDefinition` | `arn:aws:ecs:us-east-1:ACCOUNT_ID:task-definition/rails-app:*` (the family; revisions are not known in advance) |
| deploy-`<env>` | `iam:PassRole` | the `rails-app-task` and `rails-app-task-execution` role ARNs only, with condition `iam:PassedToService = ecs-tasks.amazonaws.com` |

Enable tag immutability on the ECR repository so a SHA tag, once pushed, cannot be replaced.

Naming convention across services: `github-actions-<repo>-push` and `github-actions-<repo>-deploy-<env>` for the CI roles, `<service>-task` and `<service>-task-execution` for the runtime roles. The Identity Server ADR follows the same pattern.

### ECS service settings

The service itself must be created with:

- `deploymentConfiguration.deploymentCircuitBreaker = { enable: true, rollback: true }`. This is the platform-level rollback. The pipeline's explicit rollback covers the cases the circuit breaker does not (service never reaches steady state without a hard task failure) and guarantees the notification. It is idempotent: it reads the service's PRIMARY deployment first, and if the circuit breaker already put it back on the recorded revision, it only waits for stability rather than forcing a second deployment. The Slack message says which mechanism did the rollback.
- `minimumHealthyPercent = 100`, `maximumPercent = 200`, so a deploy never reduces capacity.
- `healthCheckGracePeriodSeconds = 60`, giving `db:prepare` in the entrypoint room to run before the ALB starts counting failures.
- A task definition `healthCheck` block mirroring the Dockerfile `HEALTHCHECK` (Fargate ignores the Dockerfile one). The exact command is in the Dockerfile comments.

### GitHub repository configuration

- Secrets: `AWS_ACCOUNT_ID`, `ECR_REPOSITORY`, `SLACK_WEBHOOK_URL`, and `RAILS_MASTER_KEY` if the test suite needs it.
- Environments `production` and `staging`. Staging has no protection rules; it is where branches get tested. Required reviewers on `production` are optional and not part of this design. If a team wants them, the `environment:` key on `deploy` makes it a one-click setting that prompts once per run.
- Branch protection on `main` requiring a pull request review and the `RSpec` and `Brakeman` checks. This is the production gate. Deploys only happen from `main`, so this is what makes "reviewed and tested before deploy" true.

## Adopting the pipeline in another Rails service

1. Copy `.github/workflows/rails-deploy.yml` and `Dockerfile` into the repo.
2. Change `ECS_TASK_FAMILY`, `ECS_SERVICE`, and `CONTAINER_NAME` in the `env:` block. Nothing else in the file is service-specific.
3. Create the three IAM roles, the two GitHub environments, and the secrets above.
4. Add `brakeman.ignore` if the repo has a pre-existing Brakeman backlog. The pipeline fails on medium-or-higher confidence findings by default, and it should; a new service should start clean.
5. Push a branch. CI runs. Merge to `main`. Production deploys.

## Intentionally scoped out

Things I chose not to do in the time budget, with what I would do given more:

| Scoped out | Why | With more time |
|---|---|---|
| Terraform for the ECS service, ALB, RDS, IAM, and VPC described in the ADR | The exercise asks for the ADR, not the implementation. The ADR is specific enough to be the spec for it. | `infra/identity-server/` module in Terraform with the task definition, auto scaling policies, and alarms from OBSERVABILITY.md. ADR Definition of Done item 8 already requires this. |
| CodeDeploy or ECS-native blue/green for the Rails service | Requires a second target group and listener rule that were not in the exercise's given infrastructure. Rolling + circuit breaker + explicit rollback meets the requirement. | Move to ECS native blue/green with a 10% canary listener rule and CloudWatch alarm gates on the deployment. Rollback becomes intrinsic (green fails before the listener shifts, so traffic never leaves blue) and the pipeline's rollback step is deleted; only deregister and notify remain. |
| A working `bin/docker-entrypoint` and sample Rails app in this repo | Would make `docker build` runnable but adds a few hundred lines of generated code that says nothing about my judgment. | Add a minimal generated app so a reviewer can run `docker build --target runtime .` and the pipeline end to end against a sandbox account. |
| Native arm64 build runners | QEMU emulation works and is simpler to explain; it is just slow. | Build matrix with `ubuntu-24.04-arm` for the arm64 half and a manifest merge step. Roughly halves deploy build time. |
| Image signing and SLSA provenance | `provenance: false` is set in the pipeline to keep the ECR manifest simple. | Enable provenance, sign with `cosign` via OIDC keyless signing, and add an ECS admission check. |
| Migration of Azure AD Domain Services | Deliberately excluded from the ADR to keep the migration single-purpose. | Follow-up ADR evaluating AWS Managed Microsoft AD vs. removing the LDAP dependency in favor of a synced user store in RDS. Target: one quarter after cutover. |
| .NET 6 to .NET 8 upgrade | Same reason: one change at a time. | First sprint after ADR Definition of Done. Containerization makes this a Dockerfile base-image change plus a test cycle. |
| Cost model | No numbers were given for the Azure side. | 30-day comparison after cutover, per ADR Definition of Done item 9. |
| Per-tenant SLOs and dashboards | Needs a `tenant_id` attribute on every span first, which is an application change. | Add it in the .NET 8 upgrade sprint and split the SLO dashboards by school district. |

## A note on how I used AI

I used Claude throughout, and treated it the way I would treat a strong senior engineer drafting on my behalf: fast at producing a structured first pass, verification required for every specific claim.

What I directed and own: the migration sequence (database first, then weighted compute), the decision to keep Azure AD DS in place, the "one change at a time" principle, the rollback-targets-the-running-revision rule in the pipeline, the slim-over-alpine call, and every threshold in the observability plan. Later, on review: the deploy-role-per-environment split, the decision to keep the pipeline at two GitHub environments rather than three (below), keeping `.dockerignore` even though the exercise does not list it because the Dockerfile's `COPY . .` makes it load-bearing for Part 3, and the idempotent rollback check, which came out of asking how the circuit breaker and the pipeline's rollback step interact when both fire.

What I verified rather than trusted: that `amazon-ecs-deploy-task-definition@v2` strips read-only fields from a `describe-task-definition` dump (it does); that Fargate ignores Dockerfile `HEALTHCHECK` (it does, hence the task definition mirror); that `ENV` in a Dockerfile does not expand shell substitutions (it does not, which caught an arm64 jemalloc path bug); that Azure SQL Database supports CDC as a DMS source (it does, tier-dependent); that GitHub drops job outputs containing a secret (it does, which caught the first draft passing the full image URI between jobs, where it would have arrived empty); that GitHub environment approvals are per job rather than per run (they are, which is why `build` declares no environment and has its own push role; an earlier draft put `production` on both jobs, which would have prompted reviewers twice); that the ECS task-definition APIs accept a task-definition resource ARN (they do; the first draft of the permissions table had them on `*`).

What I overrode: the first draft used the AWS X-Ray daemon and SDK for tracing. I replaced it with OpenTelemetry and the ADOT collector because the X-Ray SDK is in maintenance mode and a single instrumentation path for .NET and Ruby is worth more than following the exercise's wording literally. The first draft also claimed zero downtime for the database cutover; I rewrote it to distinguish issuance from validation because the honest version is the one I can defend in the follow-up conversation.

A second look at the build job's `environment:` key raised the double-approval problem above. Claude's first fix introduced a third GitHub environment, `ci`, with a push role scoped to it. I went back to the exercise: it describes push-to-main continuous deployment and never mentions manual approval, so the production gate is branch protection on `main` and environment reviewers are an optional extra. The simpler shape, no environment on `build` and a push role trusting `refs/heads/*`, has the same security properties with one fewer concept and uses the two environments that already exist, so that is what shipped. I kept the per-environment deploy roles from that fix because least-privilege IAM is something the exercise evaluates by name and the change is one line.

What I verified locally: `actionlint` with `shellcheck` on every `run:` block (clean; one false positive on JMESPath backtick literals, rewritten to the raw-string form), `hadolint` (clean, one deliberate `DL3008` ignore explained in place), and `docker build --target base` for amd64 and arm64 to confirm the jemalloc symlink resolves on both. The later stages need a real Rails app in the build context, which this repo intentionally omits.

Not verified, and would be before merging: a full image build against a real Rails 8 app, and a DMS dry run against a real Azure SQL source.
